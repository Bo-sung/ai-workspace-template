# Commit Write Checklist

> Pick the target Git repository before any `git` command. See
> `.agents/rules/commit_policy.md` "Git Repository Discovery".

1. **Pick repo:** resolve the Git root for the files being committed with
   `git -C <path> rev-parse --show-toplevel`. Use `git -C <repo>` for every
   command.
2. **Stage only the intended files.** No blanket `git add .` or `git add -A`;
   those routinely pull in sensitive or unrelated changes.
3. **Re-read `commit_policy.md` "Forbidden Patterns"** right before writing the
   message. Project policy overrides any tool default that wants to append
   co-author lines, model signatures, robot emoji, or generated-by lines.
4. **Write a concise conventional commit message** (`feat:` / `fix:` / `docs:` /
   `chore:` / `refactor:` / `test:` / `build:`). Keep the subject under about 70
   characters; wrap the body; focus on why.
5. **Self-check the message** before committing:
   - No `Co-Authored-By:` line.
   - No generated model or tool signature.
   - No `Generated by` or `Generated-by`.
   - No promotional emoji or boilerplate.
6. **Verify the commit-msg hook is active** in the target repo when the project
   requires it. The hook is a defense in depth; the message must already be clean
   before invoking it. Do not run with `--no-verify`.
7. **Create the commit** from the real Git root using
   `git -C <repo> commit -m "<message>"`. For multiline messages, use a commit
   message file that you review before committing.
8. **Capture the commit hash** from the command output.
9. **Run `git -C <repo> status`** to confirm a clean tree or the expected
   remaining changes.
10. **Report** the hash, the remaining working tree state, and which repo was
    committed to. If the hook rejected the message, repair it and re-commit; do
    not bypass.
